# Live Lyric Ribbon Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the existing native lyric ribbon follow local Bopify playback correctly in Debug builds, including reading hold, repeat-one, seeks and engine replacement.

**Architecture:** Observe the stable `PlayerModel` through the existing native observation pattern; keep its single engine-event consumer. Two player revisions identify confirmed playthrough and seek transitions. A focused app session adapts domain lyrics, rejects stale loads, owns a visible-only display clock and presents the existing ribbon through Debug menu actions.

**Tech Stack:** Swift 6, Swift Testing, Observation, SwiftUI, AppKit/TextKit, Xcode 27, macOS 26; existing Rust/librespot lyric bridge unchanged.

**Spec:** [Approved live ribbon design](../specs/2026-10-18-live-lyric-ribbon-design.md), approved October 18, 2026.

**Execution:** Native, preserving the user's selection. Implement here with one fresh whole-change review at the end; commit cohesive tasks and push directly to `main`. Do not create a worktree or PR.

## Global Constraints

- Local playback first. All live ribbon types, app ownership and menu actions remain behind `#if DEBUG`; no Release entry point or automatic opening.
- Preserve the existing retro Liquid Glass shell, selectable text, focus behavior, accessibility fallbacks and standalone fixture preview.
- `PlayerModel` stays the only `engine.events` consumer. Reuse `displayPositionMs(at:)`, `displayDurationMs` and `isPositionAdvancing`; do not accumulate a second playback position.
- Display delay is exactly `.milliseconds(100)`, only while visible, eligible and advancing. Cancel pending work on invalidation and reject stale wakes by generation.
- Identity includes engine epoch, playback revision, optional queue occurrence ID and track URI. Seeks advance a separate revision; clock jumps do not invent seeks or occurrences.
- Use the existing `requestLyrics(for:)`, deadlines, limits and failure taxonomy. No Rust/C ABI, dependency, authentication, session configuration, lyric disk cache, remote mirror, translation or AI changes.
- Preserve line order, repeated words/timestamps, empty cues, provider attribution, language and RTL. Missing lyrics are not evidence of an instrumental recording.
- Reading/window actions issue no playback commands. Lyric-service failures never trigger logout or playback recovery; actual current-epoch session loss uses the existing recovery path.
- `Bopify/Bopify/Localizable.xcstrings` already has uncommitted changes: do not edit, stage, restore or regenerate it. Snapshot its hash in ignored task scratch at execution start; use `SWIFT_EMIT_LOC_STRINGS=NO` on Xcode checks. Put only new strings in `Bopify/Bopify/Lyrics/LyricRibbon.xcstrings`, using `table: "LyricRibbon"`. The native `String(localized:defaultValue:table:)` supports a separate table. [Apple String localization initializer](https://developer.apple.com/documentation/swift/string/init(localized:defaultvalue:table:bundle:locale:comment:)).
- New logs contain lifecycle transitions and outcome categories, never lyric bodies, raw responses, provider text or credentials. Use original fixture words for screenshots; do not persist screenshots of real Spotify lyrics.

## Review Focus

- Repeat-one can emit `TrackChanged` without `Loading`, with the same URI and queue entry; clear held text and invalidate the earlier playthrough anyway (Tasks 1/3).
- Queue and audio metadata can arrive in either order, including two consecutive entries of the same recording; never retain a passage under a mismatched input (Task 3).
- A cancelled old request can finish while a newer request is pending; it must neither apply a result nor clear the newer task's cancellation handle (Task 3).
- Focusing an already-visible held ribbon must not reload content, reset its scroll position or issue playback commands (Tasks 3/4).
- Attribution can wrap on a narrow display; it must not push controls offscreen or change panel geometry during cue ticks (Task 2).
