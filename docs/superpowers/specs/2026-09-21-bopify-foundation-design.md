# Bopify — Foundation and First Feature

**Status:** approved design, ready for implementation planning
**Date:** 2026-09-21
**Scope:** initial repository structure, the provider-agnostic playback seam, and the first user-visible feature ("sign in → hear audio")
**Supersedes nothing.** Complements `PRD.md`; where the two disagree, the deviations in §11 govern and say why.

---

## 1. Context

`PRD.md` specifies a native macOS menu-bar Spotify mini player that plays audio **locally on the Mac** via librespot, rather than remote-controlling another Spotify client. This document covers only what is needed to stand the project up and ship one vertical slice. Later MVP features (seek, volume, save, Now Playing, Settings, diagnostics) are explicitly out of scope here and get their own cycles.

Two product decisions were taken before design and constrain everything below.

**Distribution: personal tool, built from source.** No notarized installer, no App Store, no Spotify Extended Quota application. This is not modesty — it is the only reachable option. Spotify Development Mode is capped at **5 allowlisted users**, and Extended Quota now requires a launched service with **250k+ MAU**, with Spotify stating over 95% of applications fall short. The app was never distributable regardless of the librespot question.

**"Production-grade" therefore means engineering quality, not release ceremony:** strict concurrency, a real test boundary, no speculative abstraction.

**First feature: the sign-in → audible-track vertical slice.** Chosen to retire the largest risk first (see §7).

## 2. Decisions

Each decision records the alternative rejected and why, so a future reader can tell a considered choice from an accident.

### 2.1 Wrap `Spirc`, not `Player`

**Decision:** the Rust layer wraps `librespot-connect`'s `Spirc`, with `Player` underneath it.

`Player`'s entire surface is `load / preload / play / pause / stop / seek`. Queue, playback context, `next`, `prev`, `shuffle`, `repeat` and `set_volume` all live on `Spirc`. The PRD's `PlaybackEngine.next()/previous()` has **no backing implementation** without it.

This is corroborated by outcome, not only by signature: Speck wrapped raw `Player`, still lists next/previous, queue and autoplay as unimplemented, and has been dormant since Nov 2024. The two healthiest Swift+librespot projects (Spotifly, Spotty) both depend on `librespot-connect`.

`Spirc::activate()` makes the app the active Connect device without requiring a second Spotify client to be running. Since 2026-09-26 Bopify no longer calls it directly: the patched connect handler activates only when it has content to load (see `2026-09-26-startup-restore-design.md`).

**Rejected:** raw `Player` only — strictly narrower for no structural gain; a helper-process/IPC design around `go-librespot` — credible (very active, has an AudioToolbox macOS backend) but adds a second binary and process supervision, and no project in this ecosystem does it.

### 2.2 This also resolves a hole in the PRD

The PRD's MVP has **no way to choose what to play**: search, library browsing, playlists and queue are all v1+, yet the state machine contains `ReadyIdle --> Loading: Playable item requested` with nothing in scope able to issue that request. Taken literally, the MVP ships a player that can only ever be idle.

Being a Connect device closes this: the user's phone, desktop Spotify, or the web player becomes the content picker and hands off to Bopify. `LoadRequest::from_context_uri` allows in-app context loading later without redesign.

### 2.3 Hand-authored C ABI surface, not UniFFI or swift-bridge

**Decision:** a narrow `extern "C"` surface over an opaque handle, header generated by cbindgen and committed.

All six surveyed Swift+librespot projects use hand-written or cbindgen C FFI. None uses UniFFI. UniFFI has no stream primitive and documents that its async bindings do not conform to `Sendable` under Swift 6 (uniffi#2448) — which is precisely our event-push case on our Swift 6 target. swift-bridge marks both `Arc<T>` and `Box<dyn Fn(..)>` as "Not yet implemented", and librespot hands us `Arc<Player>` and `Arc<dyn Mixer>`.

### 2.4 Events cross the boundary as JSON

**Decision:** one `bopify_event_cb` delivering a UTF-8 JSON payload, decoded by a single `Codable` type in Swift.

librespot has 21 `PlayerEvent` variants. Both swift-bridge projects ended up hand-mirroring that enum, one leaving the comment *"basically a redefinition of librespot's PlayerEvent because of ✨ bridge reasons ✨"*. One decode beats 21 hand-mirrored variants that drift silently on every librespot bump. Events are low-frequency; serialisation cost is irrelevant at this rate.

### 2.5 The engine emits events and does not expose state

**Decision:** `PlaybackEngine` exposes `AsyncStream<PlaybackEvent>` and commands. `PlaybackState` lives on a `@MainActor @Observable` facade that folds events into it.

The PRD places `var state: PlaybackState { get }` on the engine. Being a Connect device makes that wrong: another device can pause us, skip us, change volume, or take the device away. State is never something the engine is *told* — it is something we *observe*. Events are the only honest source. This also makes `StubEngine` trivial: a continuation plus a script of events.

### 2.6 The engine is not a Swift `actor`

**Decision:** `@MainActor @Observable` facade; blocking work pushed off-main with `@concurrent`.

Under SE-0461 (Swift 6.2) a `nonisolated async func` runs on the **caller's** actor. An `actor`-typed engine called from MainActor views would therefore drag blocking FFI work onto MainActor — the opposite of the intent.

### 2.7 Views live in the app target, not in a package

SwiftUI's `Text(_:tableName:bundle:comment:)` defaults `bundle` to `nil`, documented as *the main bundle*. `Text("key")` inside a Swift package therefore searches the **app** bundle and silently renders the raw key. Keeping views in the app target removes the failure mode rather than relying on every view remembering `bundle: .module`.

### 2.8 `NSStatusItem` + `NSPanel`, not `MenuBarExtra`

`MenuBarExtra` with `.menuBarExtraStyle(.window)` has no API to dismiss the window programmatically and no access to the underlying `NSStatusItem` or `NSWindow` (FB11984872, open since 2023-02-09, still unaddressed in Xcode 27). A mini player must dismiss on action and hold key status through a drag. `MenuBarExtraAccess` exists solely to patch these gaps.

**Implementation:** `NSStatusBar.system.statusItem(withLength: .variableLength)` plus an `NSHostingView` inside a borderless `.nonactivatingPanel` with `level = .statusBar` and `canBecomeKey = true`. `LSUIElement = true`.

### 2.9 arm64-only

The target machine is arm64 and the app ships to one person. This removes `lipo`, the universal-binary step, and the `MACOSX_DEPLOYMENT_TARGET` mismatch trap (rustc defaults arm64→11.0 but x86_64→10.12, which must match the Xcode target). One line in `scripts/build-rust.sh` restores it if ever needed.

### 2.10 Cargo runs out-of-band, never as an SPM plugin

SwiftPM build-tool and prebuild plugins run sandboxed with **no network access** and restricted writes. Cargo requires both. `scripts/build-rust.sh` produces the `.xcframework`; `.binaryTarget` consumes it. `binaryTarget` cannot carry linker settings, so `.linkedFramework(…)` entries — sourced from `rustc --print=native-static-libs` — go on the wrapper target.

### 2.11 Pin librespot to a git revision

There is no stable librespot API to depend on. 0.8.0 (2025-11-10) is ten months old; `Spirc::clear_queue` and the OAuth device flow exist only on `dev`; one downstream project reports a `vergen-lib` version conflict in 0.8.0. Every surveyed Swift project vendors, forks, or pins a revision. We pin one revision, record it, and treat upgrades as deliberate work.

### 2.12 Authentication is implemented in Swift

**Decision:** PKCE, the loopback listener, token exchange and Keychain storage are Swift; the Rust layer only ever receives an access-token string.

`librespot-oauth` could do the whole flow, but auth state, the error taxonomy, and all recovery UI are Swift concerns, and Keychain is a Swift API. Doing it in Swift keeps the FFI surface purely about playback and keeps the auth flow unit-testable without the Rust library present.

**Amendment, 2026-09-21 (Task 2 spike):** the PKCE, loopback-listener and token-exchange design above is unchanged and correct. What changes is the client ID and the redirect path: the client ID must be librespot's first-party ID, not a Developer Dashboard registration, and the redirect path is `/login`, not `/callback`. Evidence is the three-run table in `docs/superpowers/specs/2026-09-21-spike-findings.md` — a dashboard client ID is rejected by `login5` with a raw HTTP 400 even when token and session both use it consistently, so it is inadmissible, not merely mismatched. The registered dashboard app is retained only for possible future Web API use, which this slice does not need.

## 3. Repository structure

```
bopify/

├── Config/
│   ├── Shared.xcconfig            SWIFT_VERSION=6, MACOSX_DEPLOYMENT_TARGET
│   └── Bopify.xcconfig
├── App/                           buildable folder (PBXFileSystemSynchronizedRootGroup)
│   ├── BopifyApp.swift            @main, LSUIElement=true
│   ├── MenuBar/                   NSStatusItem, StatusPanel, NSHostingView
│   ├── Views/                     SwiftUI views
│   ├── Localizable.xcstrings
│   └── Bopify.entitlements
├── Packages/BopifyCore/
│   ├── Package.swift              tools 6.0, defaultLocalization "en", swiftLanguageMode(.v6)
│   ├── Sources/
│   │   ├── BopifyDomain/          models + protocols; zero dependencies
│   │   ├── BopifyAuth/            PKCE, loopback listener, token exchange, Keychain
│   │   ├── BopifyPlayback/        LibrespotEngine, StubEngine, event decoding
│   │   └── CBopifyCore/           binaryTarget wrapper + linkerSettings
│   └── Tests/{DomainTests,AuthTests,PlaybackTests}
├── rust/
│   ├── Cargo.toml                 workspace; pins librespot revision
│   └── crates/bopify-core/        extern "C" surface over Spirc
├── scripts/
│   ├── build-rust.sh              cargo → .a → .xcframework
│   └── gen-header.sh              cbindgen
└── docs/superpowers/specs/
```

**Buildable folders** (Xcode 16+) record only the folder path in the project file without enumerating contained files. Adding a source file is therefore *writing a file* — no `.xcodeproj` mutation and no merge conflict. Target, scheme and build-setting changes still rewrite `pbxproj`, so build settings live in `.xcconfig`.

**Three package targets, and no more.** `BopifyDomain` has zero dependencies, so tests and views import the models without linking the Rust library. `BopifyPlayback` is the only target that touches the FFI. `BopifyAuth` is independently testable against a local fake. A fourth cannot be justified today; per `AGENTS.md` §2, a split that cannot be defended is speculative.

**Set on day one because retrofitting churns everything:** `SWIFT_VERSION = 6` (Xcode 27's app template still ships `5.0`, and approachable-concurrency build settings are *not* the same as Swift 6 language mode), and `defaultLocalization: "en"`.

## 4. Domain model and the seam

```swift
public protocol PlaybackEngine: Sendable {
    var events: AsyncStream<PlaybackEvent> { get }

    func load(_ request: PlayRequest) async throws
    func resume() async throws
    func playHere() async throws
    func pause() async throws
    func next() async throws
    func previous() async throws
    func seek(to milliseconds: Int64) async throws
    func setVolume(_ value: Double) async throws
}
```

`seek` and `setVolume` are declared because the ABI exposes them and `StubEngine` implements them; **no UI in the first slice calls them** (§7).

`PlaybackState` follows `PRD.md` §"Core models" with one addition:

```
PlaybackState
  phase, currentTrack, positionMs, durationMs, volume,
  canSeek, canPrevious, canNext,
  isActiveDevice: Bool        ← added
  error: PlayerError?
```

`isActiveDevice` is required because the PRD's state machine has no transition for *another device took over*. Without it the UI shows a phantom paused track indefinitely.

`AuthService`, `Track`, `PlayRequest`, `AuthState` and `PlayerPreferences` are taken from `PRD.md` unchanged.

## 5. The C ABI

Roughly ten functions over an opaque handle. Indicative shape; exact signatures are settled in implementation and the header is generated by cbindgen and committed.

```c
typedef struct BopifyEngine BopifyEngine;
typedef void (*bopify_event_cb)(const uint8_t *json, size_t len, void *ctx);

BopifyEngine *bopify_engine_create(const char *access_token,
                                   const char *device_name,
                                   bopify_event_cb cb, void *ctx,
                                   int32_t *out_err);
void    bopify_engine_destroy(BopifyEngine *);
int32_t bopify_play(BopifyEngine *);
int32_t bopify_play_here(BopifyEngine *);
int32_t bopify_pause(BopifyEngine *);
int32_t bopify_next(BopifyEngine *);
int32_t bopify_previous(BopifyEngine *);
int32_t bopify_seek(BopifyEngine *, uint32_t position_ms);
int32_t bopify_set_volume(BopifyEngine *, uint16_t volume);
int32_t bopify_load(BopifyEngine *, const char *context_uri,
                    const char *start_track_uri /* nullable */,
                    uint32_t start_position_ms);
int32_t bopify_update_token(BopifyEngine *, const char *access_token);
const char *bopify_error_message(int32_t code);
```

`bopify_activate` was removed on 2026-09-26 with the startup-restore change. `bopify_load` carries all three `PlayRequest` fields — `contextURI`, `uri` (as the starting track, mapping to `PlayingTrack::Uri`) and `startPositionMs` — so the protocol and the ABI express the same thing. Earlier drafts of this section omitted both, which would have forced the implementer to invent a resolution mid-slice.

**Audio output** uses librespot's default `rodio` backend (cpal → CoreAudio), which needs no Homebrew packages on macOS. `Player::new` takes a `sink_builder`, so replacing it with a proxy sink feeding `AVAudioEngine` later — as Spotty does, to work around librespot #547 (output-device changes not honoured on macOS) and #1057 — is a localised change behind an existing seam. Accepted for now: changing output device mid-playback may not take effect.

## 6. Concurrency and data flow

```
librespot tokio thread ──cb──▶ AsyncStream.Continuation.yield
                                        │
                                        ▼
                        single .task owned by the facade  (@MainActor)
                                        │  folds events into PlaybackState
                                        ▼
                                  SwiftUI views
```

- The C callback trampolines through an unretained context pointer (`Unmanaged<…>.passUnretained`) into the stream continuation. `AsyncStream.Continuation` is documented `Sendable`, so yielding from the Rust thread is expected to be safe — but this is the one mechanism claim here that has not been exercised, so step 2 verifies it under strict concurrency rather than assuming it.
- **One** consumer task, owned by the facade — not a per-view `.task`, which re-subscribes whenever view identity changes.
- Session creation and token refresh are pushed off-main with `@concurrent`. Transport commands are expected to be non-blocking channel sends (§10, Q4).
- Commands are **requests**. Authoritative state arrives only as events. This already matches the PRD's "authoritative engine state wins" and generalises it to externally-initiated change.

**Token refresh is a correctness requirement.** Access tokens live 3600 s and expiry silently kills the Spirc session — NullSpot encodes a dedicated error code for exactly this. Swift refreshes ahead of expiry and pushes the new token via `bopify_update_token`. **Amended 2026-09-22: there is no rebuild path, and this slice does not add one.** `bopify_update_token` always reports `SessionLost` because librespot exposes no documented way to swap credentials in place, and nothing reconstructs the engine outside sign-in. So when a session dies the panel shows the `playbackSessionLost` error and stays there: the app is still signed in, so no sign-in button is offered, and the only recovery is right-click -> Sign Out -> Sign In. Commands keep returning success throughout, because the Rust handle is still alive. Rebuilding the session belongs to a later slice. Refresh tokens issued to Dashboard-registered apps last **6 months** and refreshing does not extend that, so a forced interactive re-auth twice a year is expected behaviour, not a defect.

## 7. First feature — Bopify 0.1

**User-visible outcome.** The menu-bar icon opens a panel offering "Sign in with Spotify". Consent happens in the browser. Playback then starts **from this Mac** — by default via Connect handoff, with the Mac appearing as a device named *Bopify* in the user's phone, desktop Spotify or web player. Should Q5 (§10) resolve against handoff, the same slice starts playback from a known context URI instead; either way audio originates locally. The panel shows artwork, title, artist, elapsed and duration, with working play/pause, next and previous.

**In scope:** PKCE sign-in, Keychain persistence, session restore on relaunch, Spirc session and activation, the event loop and state projection, the menu-bar panel with its signed-out / authenticating / idle / loading / playing / paused / error presentations, and play/pause/next/previous.

**Out of scope, deliberately:** seek and volume — continuous controls introduce preview-position-versus-authoritative-state semantics, a distinct problem deserving its own slice. Also out: save/heart, Now Playing and media keys, Settings, diagnostics, shuffle/repeat, search, library.

Next and previous are included because they are the same one-line command through the same ABI and the same reconciliation path. They add no architecture.

**Scopes requested:** `["streaming"]` only — what librespot's own `play_connect.rs` uses. The 26-scope bundle in librespot's CLI (`OAUTH_SCOPES` in `main.rs` at pinned revision `939dc5e`) mirrors the Spotify desktop app and carries its own warning that some entries are only available to Spotify's client IDs.

### Ordered steps

| # | Step | Verification |
|---|------|--------------|
| 0 | Spotify app registered with redirect `http://127.0.0.1/callback` (no port); account added to the Development Mode allowlist; Premium confirmed | manual; blocks all later steps |
| 1 | Pin librespot revision; Rust binary connects via Spirc, answers Q5, and plays a context | `cargo run` — **audio audible before any Swift exists** |
| 2 | C ABI, cbindgen header, `.xcframework` | `swift test` links and asserts an invalid token yields the expected error code |

**Step 1 is first by design.** The riskiest assumption in the project is "librespot builds and plays on macOS arm64", and librespot's CI matrix is `[ubuntu-latest, windows-latest]` — PR #1671 adding macOS has been open since 2025-12-28. **We are the macOS coverage.** Proving it in Rust alone costs an afternoon; discovering it after a Swift app exists costs the project.

## 8. Error taxonomy for this slice

Only the reachable subset of `PRD.md`'s taxonomy is implemented: `authDenied`, `invalidCallback`, `authExpired`, `premiumRequired`, `networkUnavailable`, `playbackSessionLost`, `unknown`.

`premiumRequired` is load-bearing rather than cosmetic: Spotify removed the `product` field from `GET /v1/me` in February 2026, so **a librespot session failure is the only available Premium signal**. It must be mapped explicitly, not folded into `unknown`.

The remaining PRD errors (`libraryMutationFailed`, `rateLimited`, `seekFailed`, `trackUnavailable`) belong to features not in this slice. Implementing them now would be error handling for scenarios that cannot occur (`AGENTS.md` §2).

## 9. Testing and verification boundary

**Automated — `swift test`:** everything above `PlaybackEngine`, driven by `StubEngine`; PKCE challenge/verifier derivation and token exchange against a local fake endpoint, including failure paths; JSON event decoding against fixtures captured from the real engine.

**Automated — `cargo test`:** error-code mapping and event JSON encoding in the ABI layer.

**Manual acceptance:** audio output, browser consent, and Connect-device handoff.

"You hear music" is not an assertion. It is labelled a manual acceptance check rather than dressed up as a test.

Swift Testing (`import Testing`, `@Test`/`#expect`) ships with the toolchain and runs under plain `swift test`. It is **not** auto-selected — the Xcode 27 test-bundle template ships a Testing System default of `None`, so it is chosen explicitly at target creation. XCTest is reserved for any future XCUITest smoke test, since UI automation and performance metrics remain XCTest-only.

## 10. Open questions, to be resolved during steps 1–3

These are resolved by doing, not by deciding now. Each has a defined fallback.

- **Q1 — Does `TrackChanged` carry title/artist/artwork?** If it does, this slice needs **no Web API at all**: no HTTP client, no rate-limit handling, no OpenAPI generation. Fallback: one `GET /v1/tracks/{id}` per track. Note there is no bulk track endpoint any more — `GET /v1/tracks` was removed in February 2026 — so per-track fetching against a 30-second rolling window is the only option if needed.
- **Q2 — Which librespot revision?** Resolved in step 1 by building. Expected to be a `dev` revision rather than the 0.8.0 tag, given the reported `vergen-lib` conflict.
- **Q3 — Does the data-protection Keychain work under local development signing? — RESOLVED 2026-09-21: no.** `kSecUseDataProtectionKeychain: true` returns `errSecMissingEntitlement` (-34018) on every save and clear under this repo's signing, with no Xcode project or provisioning profile present. TN3137's requirement does bind the default access group, not only named ones. The documented fallback is taken: `KeychainTokenStore` uses the legacy file-based keychain. Revisit only if the app later ships with an embedded provisioning profile. Independently, "refresh token missing → silently re-run OAuth" ships from day one, because changing Team ID orphans every stored item.
- **Q4 — Are Spirc commands non-blocking?** Assumed yes (they are queued channel sends). If any blocks, route it through `@concurrent` as well.
- **Q5 — Does the device actually appear in the user's Spotify client list?** This is the load-bearing one. We authenticate with an OAuth token via `Credentials::with_access_token` and call `activate()` — the *authenticated* path, not the `with-libmdns` zeroconf-discovery path. Whether a token-authenticated device is offered for handoff in the user's other Spotify clients is unconfirmed. **If it is not, the content-selection story in §2.2 fails and the slice has no way to start playback.** Fallback, already present in the ABI: drive `bopify_load` with a known playlist or album URI, and treat in-app context selection as the entry point instead of handoff. Step 1 must answer this before any Swift is written.

## 11. Deviations from `PRD.md`

| PRD | Change | Reason |
|-----|--------|--------|
| `PlaybackEngine` exposes `var state` | Exposes `AsyncStream<PlaybackEvent>`; state moves to the facade | As a Connect device, state is observed, never told (§2.5) |
| `PlaybackState` fields | Added `isActiveDevice: Bool` | No transition existed for "another device took over" |
| MVP content selection unaddressed | Connect handoff is the picker | §2.2 |
| Scope table implies `playlist-modify-public` | Ship `user-library-read` / `user-library-modify` when Save arrives; verify empirically | Spotify's reference page lists the **union** of scopes across all library URI types, not per-call requirements |
| `GET /me` `product` for Premium | librespot session failure is the Premium signal | Field removed February 2026 |
| Metadata "via librespot and/or Web API" | Prefer librespot; Web API only if Q1 fails | Removes an entire dependency from the slice if unnecessary |

**Consent cost, accepted knowingly:** Spotify has no incremental consent. Requesting `streaming` now and adding `user-library-*` when Save ships re-runs the full browser flow. This follows directly from PRD A9 and is a deliberate trade, not a surprise.

## 12. Accepted risks

- **Spotify Developer Terms.** No clause names librespot, but Developer Policy III.11 (do not replicate a core Spotify user experience) and Developer Terms IV.2.1.b (no reverse-engineering of the Spotify Platform) both bear on a reverse-engineered protocol client. Accepted under PRD A13 given personal, non-distributed use. *(Clause numbers came from an automated page read and should be re-checked against the live text before being quoted anywhere externally.)*
- **librespot has no macOS CI.** We are the coverage.
- **No stable librespot API.** Pinned revision; upgrades are deliberate work.
- **Output-device changes mid-playback may not be honoured** (librespot #547). Mitigated later by swapping the sink, behind an existing seam.
- **librespot is MIT-licensed throughout**, so the licence is clean; the risk is Spotify's terms, not copyright. Transitive dependency licences are unaudited.
